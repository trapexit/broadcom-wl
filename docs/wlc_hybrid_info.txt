WLC HYBRID BINARY DRIVER EVALUATION
===================================

Analysis date: 2026-07-17
Target: lib/wlc_hybrid.o_shipped
Method: read-only static metadata, symbol, relocation, and printable-string
        inspection. The object was not loaded or executed.


1. EXECUTIVE SUMMARY
--------------------

lib/wlc_hybrid.o_shipped is Broadcom's proprietary, precompiled half of the
64-bit wl Linux wireless driver. It is a structurally valid, unstripped ELF64
x86-64 relocatable object, not a complete loadable kernel module. The repository
links it with the open-source Linux glue in src/shared/linux_osl.c and
src/wl/sys/*.c to produce wl.ko.

The object identifies itself as driver 6.30.223.271 (revision r587334). Its two
embedded PCI firmware images identify themselves as 6.30.223.0 and carry
2013-12-15 build dates. The compiler record is GCC 4.4.7 from 2012. The repository
README declares the driver unmaintained, so the age and fixed precompiled code
are the principal maintenance and assurance concerns.

The binary retains a rich symbol table: 2,722 named functions, 1,284 named data
objects, and 111 source-file records. Only 41 functions are globally exported.
All 85 unresolved imports go through Broadcom's osl_* OS abstraction, wl_* Linux
glue, or g_assert_type; there are no direct unresolved Linux kernel API symbols
in this object. This boundary lets the source wrapper absorb kernel API changes,
but it does not make the proprietary code rebuildable with current hardening or
toolchains.

No structural ELF errors were found. Static metadata alone cannot establish
correctness, freedom from vulnerabilities, exact device compatibility, runtime
stability, or regulatory behavior.


2. SCOPE AND LICENSE LIMIT
--------------------------

lib/LICENSE.txt describes the Software as binary code owned by Broadcom. Among
other conditions, it permits use/integration and distribution only complete and
unmodified for a Broadcom Product, with the agreement accompanying distribution.
It explicitly prohibits reverse engineering, decompilation, and disassembly and
provides no warranty or support. This is a technical summary, not legal advice.

To stay within that stated limit, this evaluation does not disassemble
instructions, decompile functions, reconstruct algorithms, patch the object, or
attempt to extract executable firmware. Findings are limited to standard ELF
metadata, names intentionally retained in the symbol table, relocation records,
and printable identification/diagnostic strings.

11. SECURITY AND RELIABILITY OBSERVATIONS
-----------------------------------------

Confirmed observations:

* The final code executes in kernel context and processes hardware state,
  management/control requests, and network traffic. A defect therefore has a
  potentially system-wide impact rather than ordinary user-process isolation.

* The object is fixed, closed, more than a decade old by embedded build evidence,
  built with GCC 4.4.7, and housed in an archived repository. It cannot be
  recompiled locally with current compiler diagnostics or hardening options.

* No stack-canary, FORTIFY, sanitizer, CFI, retpoline/IBT, BTF, or unwind-related
  imports/sections were found in this component. Some protections are applied by
  the kernel or final module build, but they cannot retroactively instrument the
  precompiled instruction stream. The empty GNU-stack marker is a positive but
  limited property.

* The interface includes legacy WEP/RC4 and TKIP code alongside AES/CCMP and
  WPA/WPA2. Presence supports compatibility; it does not imply that weak modes
  are selected. Deployments should avoid WEP and TKIP.

* The object references bounded and unbounded string helpers. Relocations include
  82 osl_snprintf, 33 osl_strncpy, 2 osl_vsnprintf, and one each to osl_strcpy and
  osl_sprintf. Symbol references alone cannot show buffer sizes or establish an
  overflow, so these are audit targets rather than vulnerability findings.

* Diagnostic strings include assertion file/line data and pointer formatting
  ("ASSERT in file %s line %d (ra %p, fa %p)") plus allocator diagnostics.
  Whether pointers are exposed depends on reachability, log settings, and kernel
  pointer-format restrictions.

* The ELF is internally well formed, and all proprietary-to-host dependencies
  are concentrated in a small named wrapper boundary. This is useful for kernel
  compatibility maintenance and for auditing the directly reachable Linux APIs.

Risk-relevant surfaces indicated by names, not audited implementations:

* wlc_ioctl, wlc_iovar_op, and the large wlc_doiovar control parser;
* packet receive/transmit, aggregation, security-key, and replay paths;
* wireless management-frame, information-element, channel, and regulatory data;
* srom_parsecis plus OTP/SROM/NVRAM board configuration;
* PCI/PCIe configuration, DMA, MMIO, interrupts, timers, and power management;
* host-to-embedded-firmware RPC, offload, packet-filter, scan, and wake paths.

No claim about a specific exploitable flaw or CVE is made. This pass did not
perform live CVE/version correlation, runtime tracing, fuzzing, malformed-input
testing, hardware exercise, or instruction-level control/data-flow analysis.


12. OPERATIONAL RECOMMENDATIONS
-------------------------------

1. Treat the SHA-256 above as the identity of the evaluated artifact. Recompute
   it after packaging or transfer; do not silently substitute a similarly named
   blob.

2. Prefer a currently maintained distribution package or supported driver/device
   where possible. If this driver is required for legacy hardware, limit it to a
   well-defined compatibility environment and document the accepted risk.

3. Build the final wl.ko against every exact target kernel and inspect its
   vermagic, signer, dependencies, and load diagnostics. Results for wl.ko must
   not be inferred from this intermediate object.

4. Use modern network configuration (at least WPA2 with AES/CCMP where supported)
   and disable WEP/TKIP rather than relying on their mere availability.

5. Exercise association, suspend/resume, wake, scan, heavy traffic, and error
   recovery on representative hardware. Firmware-offload and regulatory paths
   should be included because they cross host/blob/firmware boundaries.

6. Audit changes to src/shared/linux_osl.c and src/wl/sys/*.c carefully: those
   files translate kernel memory, DMA, packet, timer, interrupt, and cfg80211/WEXT
   semantics for a proprietary object whose ABI cannot be regenerated.

7. Preserve lib/LICENSE.txt and evaluate its terms before redistribution or any
   deeper binary work. Keep the proprietary object unmodified.
